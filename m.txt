# MASTER PROMPT: Network Behaviour Fingerprinting for Unseen Cyberattack Detection

## 1. PROJECT IDENTITY

**Project Title:** Network Behaviour Fingerprinting for Unseen Attack Detection: An Experimental Comparison of XGBoost and Variational Autoencoders

**Academic Level:** Advanced MSc Data Science

**Project Domain:** Cybersecurity, Machine Learning, Deep Learning, Anomaly Detection, Statistical Evaluation

**Primary Dataset:** CICIDS2017

**Implementation Environment:** Python, Google Colab, Pandas, NumPy, scikit-learn, XGBoost, PyTorch, Matplotlib, SciPy

**Project Type:** Research-oriented machine learning and deep learning project

### Core Objective

Design, implement, and evaluate a reproducible network intrusion detection framework that compares exactly two predictive models:

1. **XGBoost:** A supervised traditional machine learning classifier trained on labelled network-flow records.
2. **Variational Autoencoder (VAE):** A deep learning model trained primarily on benign network traffic to learn normal traffic representations and generate anomaly scores.

The research must investigate known-attack detection, held-out attack-family detection, false-positive behaviour, and generalisation under distribution shift.

The central research question is:

"How effectively can supervised classification and normal-behaviour modelling detect known and held-out cyberattack families, and how do their detection capabilities, false-alarm rates, and generalisation characteristics differ?"

Do not assume that either model is superior. The final conclusions must follow from actual experiments.

# PHASE 2 — COMPLETE MODEL IMPLEMENTATION AND TRAINING PIPELINES

## 2.1 Implement XGBoost

- 0 = Benign.
- 1 = Attack.

Preserve original attack-family labels separately for evaluation.

### Requirements

- Support imbalanced class distributions.
- Use a documented hyperparameter search space.
- Select hyperparameters using training and validation data only.
- Use validation-based threshold selection.
- Save the fitted model and its configuration.
- Save prediction probabilities rather than only class labels.
- Record training duration and inference duration.
- Record the feature schema used by the trained model.
- Ensure reproducibility through controlled random seeds.

Investigate class weighting or other appropriate imbalance handling, but never rebalance the final test data artificially.

Do not choose hyperparameters using final test performance.

## 2.2 Implement the Variational Autoencoder

Implement the VAE using PyTorch.

Use a configurable encoder-decoder architecture suitable for tabular network-flow data.

### Encoder

The encoder maps the input feature vector into:

- Latent mean vector.
- Latent log-variance vector.

### Latent sampling

Implement the reparameterisation trick so the model can be trained using gradient-based optimisation.

### Decoder

The decoder reconstructs the input feature vector from a sampled latent representation.

### Training objective

Use a configurable objective:

L = Reconstruction Loss + beta × KL Divergence.

The reconstruction loss must be appropriate for the chosen feature representation.

For continuous numerical features, a documented squared-error or probabilistic reconstruction objective may be used.

For a mixed feature representation, choose a justified likelihood or loss formulation rather than assuming every column is Gaussian.

The KL-divergence term must be computed correctly and its scaling must be documented.

### Training requirements

- Train primarily on benign training records only.
- Never use attack labels to train the normal-behaviour representation.
- Use benign validation data for early stopping and model selection.
- Save training and validation loss histories.
- Support CPU execution and CUDA when available.
- Use mini-batches and configurable batch sizes.
- Avoid loading unnecessarily large arrays onto the GPU.
- Detect numerical instability, NaN losses, and invalid outputs.
- Save the best validation checkpoint.
- Record architecture and training hyperparameters.

### Anomaly-score definition

Implement a documented anomaly-scoring function.

A reconstruction-based score may use the mean or sum of feature-wise reconstruction errors. If feature weighting is used, justify and document it.

Investigate whether stochastic latent sampling affects score stability. Use a consistent scoring procedure for all evaluated records.

Do not describe a raw anomaly score as a calibrated attack probability.

## 2.3 Threshold selection

Define the VAE threshold using benign validation records only.

Support a configurable false-alarm tolerance, such as a predeclared percentile of the benign validation anomaly-score distribution.

The threshold must be fixed before final test evaluation.

Do not select the threshold by inspecting held-out attack labels.

Report the actual validation false-positive rate and the test false-positive rate separately.

# PHASE 3 — CONTROLLED RESEARCH EXPERIMENTS AND GENERALISATION ANALYSIS

This phase implements the actual research contribution.

All experiments must use the partition manifest established in Phase 1.

## 3.1 Experiment A: Known-attack detection

Evaluate both models on held-out benign records and attack families represented in supervised training.

Report:

- Average Precision.
- PR-AUC curves or equivalent precision-recall analysis.
- ROC-AUC.
- Precision.
- Recall.
- F1-score.
- False-positive rate.
- Confusion matrix.
- Inference latency.

Use the same evaluation records for both models wherever the comparison is methodologically valid.

State clearly that the VAE uses anomaly scores rather than supervised attack probabilities.

## 3.2 Experiment B: Held-out attack-family detection

Create one or more explicit held-out attack-family experiments.

For each experiment:

1. Exclude selected attack families from XGBoost training.
2. Ensure their records are not used in supervised validation or hyperparameter selection.
3. Train the VAE only on permitted benign training data.
4. Choose the anomaly threshold using benign validation data.
5. Evaluate both models on a test set containing benign traffic and the held-out attack families.
6. Report results separately for each held-out family.

The held-out family must not leak into model selection through attack labels, threshold tuning, feature selection, or manual adjustment.

Document whether capture conditions and time periods are shared between training and testing. A held-out label does not automatically establish independent real-world generalisation.

For XGBoost, evaluate whether the supervised classifier identifies the held-out attack records despite not being trained on that attack family.

For the VAE, evaluate whether the held-out attack records receive higher anomaly scores than benign records.

Do not assume that an unseen attack must have a high anomaly score.

## 3.3 Experiment C: False-alarm and threshold sensitivity

Evaluate the effect of different predeclared benign validation false-alarm tolerances.

For every operating point, report:

- Validation false-positive rate.
- Test false-positive rate.
- Attack recall.
- Precision.
- F1-score.
- Number of false alerts.
- Number of detected attacks.

Plot detection performance against false-positive rate.

Explain the operational implications of the trade-off.

Do not choose the most favourable threshold after observing the final test results.

## 3.4 Experiment D: Distribution-shift stress testing

Investigate how each model responds when the evaluation distribution differs from the training distribution.

Potential stress conditions include:

- Controlled changes to selected continuous features.
- Changes in traffic intensity.
- Changes in packet-size distributions.
- Changes in flow-duration distributions.
- Capture-period shifts.
- Differences in traffic composition.

Clearly separate synthetic perturbations from naturally occurring shifts.

Define each perturbation, its severity, affected features, and justification before running the final evaluation.

Do not create artificial attack labels merely because a feature value was perturbed.

Investigate whether preprocessing itself amplifies or suppresses the observed shifts.

## 3.5 Experiment E: Cross-dataset generalisation

Where feasible, evaluate the trained models using a compatible subset of CICIDS2018.

Before proceeding:

- Verify feature definitions and units.
- Align feature names and order.
- Identify unavailable or incompatible fields.
- Apply only transformations learned from the permitted training data.
- Document differences in collection conditions.
- Avoid fitting a new transformation using target-dataset statistics if that would violate the declared protocol.

Treat this as a separate generalisation experiment.

Do not compare raw scores across datasets without considering differences in prevalence, traffic composition, and feature distributions.

## 3.6 Experiment F: Complementarity analysis

Investigate records for which XGBoost and the VAE disagree.

Analyse:

- Attacks detected by both.
- Attacks detected only by XGBoost.
- Attacks detected only by the VAE.
- Attacks missed by both.
- Benign records incorrectly flagged by either approach.

Create a disagreement analysis using held-out records and fixed thresholds.

This is an analysis of the two existing models, not permission to build an ensemble.

# PHASE 4 — STATISTICAL VALIDATION, INTERPRETABILITY, AND SCIENTIFIC REPORTING

This phase determines whether the results support defensible conclusions.

## 4.1 Statistical uncertainty

Use repeated training runs with multiple random seeds where appropriate.

For key metrics, calculate confidence intervals.

Use paired bootstrap comparisons when comparing predictions from the same held-out records.

Document:

- The unit of resampling.
- The number of bootstrap replicates.
- The confidence-interval method.
- Any grouping required to account for correlated flows.

Where records are strongly correlated within capture periods, avoid treating every row as an independent observation without justification.

Do not claim statistical significance solely because one observed metric is larger than another.

## 4.2 Evaluation metrics

Use a consistent metric-definition module.

### Classification metrics

- Average Precision.
- ROC-AUC.
- Precision.
- Recall.
- F1-score.
- Confusion matrix.
- False-positive rate.
- False-negative rate.

### Anomaly-detection metrics

- Anomaly-score distributions for benign and attack traffic.
- Recall at predefined benign false-alarm tolerances.
- Precision-recall analysis using anomaly scores.
- Per-attack-family detection rates.
- Threshold sensitivity.

### Computational metrics

- Training duration.
- Inference latency.
- Throughput.
- Peak memory consumption where measurable.
- Model artifact size.

Document the hardware and execution environment for timing comparisons.

### Calibration

XGBoost probabilities and VAE anomaly scores are not inherently equivalent.

Do not compare Brier scores or expected calibration errors on these raw outputs as though both were attack probabilities.

If probability calibration is investigated, define a validation-only calibration procedure, fit it without test labels, and report calibration results separately from raw anomaly-detection performance.

## 4.3 Feature importance and interpretability

For XGBoost, use feature importance and, where practical, SHAP to investigate which features influence predictions.

For the VAE, investigate:

- Feature-wise reconstruction errors.
- Features contributing most to selected anomaly scores.
- Score differences between benign and attack groups.
- Examples of false positives and false negatives.

Avoid claiming that feature attribution establishes causation.

Explain that a feature with high reconstruction error is not necessarily the cause of an attack.

Interpretability tools must not alter the held-out test protocol.

## 4.5 Research hypotheses and interpretation

Evaluate the following hypotheses:

H1: XGBoost performs effectively on attack families represented in its supervised training data.

H2: The VAE can identify at least some held-out attack records at a controlled benign false-alarm rate.

H3: The VAE identifies some held-out attacks missed by XGBoost.

H4: Detection performance varies across attack families and evaluation conditions.

H5: Distribution shift affects the two models differently.

Each hypothesis must be evaluated independently.

A hypothesis may be unsupported or contradicted by the results. That is acceptable and must be reported honestly.
